## B. 可靠性

9. ~~**run 级重试**~~ ✅ 已完成 —— 曾是剩下最大的可靠性洞，也是第 6 处「声明了没接线」。

   `recovery: 'automatic'` 界面说「系统会自动重试」，但 attempt 失败后 run
   直接落 terminal `failed`，队列是空的。真正的重试只发生在一次 `chat()`
   内部（就地重试 + 模型链降级）。`runStatusOverride`（注释写着「failed 但
   还要重试 → waiting_retry」）**没有任何调用方传它**。

   后果就是最初抱怨的那类：四个模型同时被限流 → run 直接死 → 得重新发一遍，
   而界面还说它会自己恢复。

   已做：退避 + 上限 + 调度（`run_queue.available_at` 现成，没建新表）、
   与终态写入**同事务**（否则中间崩溃会留下「waiting_retry 但队列为空」）、
   reconciler 兜底重排、事件流记 `attempt.failed{willRetry, delayMs, reason}`。

   **过程中被迫想清楚三件事：**

   一、`retryable` 与 run 级重试**不是一回事**。前者是「就地重试」（让模型
   重写），`contract.postcondition_failed` 标着 retryable: true。照它重试会把
   「模型答不对」变成「任务反复重跑，只是慢四倍」。所以新增 `runRetryable`，
   只给「等一会儿真的会好」的那几个：限流、额度、服务端错误、超时、全链不可用。

   二、**provider 说的时间不该被我们的退避上限截断。** `min(cap, max(backoff,
   after))` 是错的：额度一小时后重置而 cap 是 5 分钟时，我们会在 5 分钟后去撞
   一扇关着的门，把 attempt 预算烧完 ——「白等 15 分钟然后失败」比「等一小时
   然后成功」差得多。上限只约束我们自己猜的退避。

   三、决策必须放在 **runner** 的失败路径，不是 worker 的 catch —— 失败被
   runner 捕获并**返回** outcome，异常根本传不到 worker。我第一版放错了，
   结果 all_exhausted 照旧落 failed，实测才发现。

   顺带：`enqueueAttempt` 原本会把 `waiting_retry` 翻成 `pending`，那样「任务
   在等什么」就看不出来了 —— 改成只有立即可执行时才翻。以及界面的恢复性提示
   现在**跟着实际行为**而不只看错误码：run 是 waiting_retry 时显示
   「已排重试 · 2:24:36 PM 自动再试」，而不是 all_exhausted 的「需要你处理」。
   后者正是我之前批评过的「界面说谎」，差点自己又犯一次。

10. ~~**compact**~~ ✅ 已完成 —— 原来超预算是**丢**最旧的消息，不是压缩。
    装配器降级顺序里的 `shrink_summary` / `drop_summary` 两档永远不会触发，
    因为没有任何代码产生摘要。现在接上了。

    **摘要是结构化的，不是散文。** 这是这一块最要紧的决定。
    「请总结上面的对话」会产出「用户与助手讨论了若干话题」这种东西 ——
    读起来像摘要，但恰好丢掉了唯一要紧的部分。真实故障形状是
    「模型忘了我三轮前说过不要用 default 模型，又开始建议我加」，
    而散文摘要挡不住它，因为它没有任何地方**必须**写下约束。

    所以用小词表 + function calling（和结果契约同一套思路）：
    `constraints`（用户原话，渲染时排最前）/ `decisions`（连同为什么）/
    `open` / `artifacts`（只引用）/ `context`。模型只负责浓缩，
    什么必须留下由 schema 强制。

    三条不变量：

    - **消息永不删除。** 压缩只写 `summary` 与 `summary_through_seq`。
      摘要失败时退化成「装配器照常裁剪」，而不是数据丢失。
      库会一直长，但那是磁盘问题；反过来是正确性问题。
    - **压缩失败不能让任务失败。** 它是锦上添花的一次调用，所以整条路径
      catch 到底，只记账不抛。（隔壁 cron 是反例：一条坏计划不 catch 会拖死 worker。）
    - **压缩发生在装配之前。** 等装配器报 `trim_history` 才动手没用 ——
      那时消息这一轮已经被丢了。

    `compactions` 表一次一行（和 `schedule_fires` 同一个理由：有损、不可逆、
    没人在旁边看的操作必须自己留账）。存「哪一代退役了哪些 seq」与
    **摘要全文** —— 「模型为什么忘了」只能靠对比这两者定位，而症状要几轮之后
    才以「它怎么又提这个」的形式出现。压缩失败也记一行：那时消息没退役、
    摘要没生成，症状却和「摘丢了」一模一样，不留账就分不开。

    过程中修掉的：

    - **mock 会消耗 agent 的脚本游标。** 压缩请求没有 system 消息，
      `whichAgent` 认不出来会随便挑一个 agent，把后面的剧本全错位 ——
      症状是「某个专家突然走了别人的分支」，极难追。现在压缩请求单独认出来。
    - **mock 把我自己 prompt 里的「## 要求」当成用户约束。** 那会让测试因为
      **错误的原因**通过：断言「约束活下来了」，活下来的其实是提示词自己的话。
    - **`compactions` 按 `created_at` 排序不稳定**（FakeClock 下多行时间戳相同），
      于是「哪一代」会指错。改成按 `id`（bigserial）—— 与之前 `bundle.ts` 按
      `intent_at` 排序那个 bug 同一类。
    - 顺带：**`--conv` 只认完整 UUID，而终端打印的是 8 位短 id** ——
      界面给了一个粘不回去的值。现在按前缀解析，撞车时报出来而不是随便挑一个
      （挑错会把消息追加到别人的会话里）。

11. **装配器另外两个空入口** —— `facts`（L2 事实层）与 `constraints`（T1 注入）
    同样没人喂。`constraints` 归 C 块；`facts` 是 L2 记忆，可以更晚。

## C. 规则

12. **规则作者单元** —— 一条规则同时携带三层，运行时按字段决定它落到哪层：

    ```jsonc
    { "id": "cite-sources",
      "constraint": "每条 finding 至少一个可验证来源。",   // T1 注入末尾约束块
      "check": { "requiredFields": ["findings[].sources"] }, // T2 校验
      "denyTools": [],                                       // T3 边界
      "appliesTo": ["researcher"] }
    ```

    两条原则：
    - **T1 必须配 T2**。只写 T1 等于把「prompt 写满禁止但模型照犯」原样搬回来
    - **能用 T3 表达的绝不写成 T1**。T3 零成本且不可违反；T1 只在无法用能力
      边界表达时才用（「结论要标来源」没有任何工具开关能阻止）

13. **T1 注入**到末尾约束块。`buildTail()` 与 `maxConstraintTokens` 预算都已存在，

## E. cron ✅ 已完成

18. ~~**`schedules` 表 + worker tick 里的 `#fireDueSchedules()`**~~ ✅ 已完成

    不需要新进程：`run_queue.available_at` 已经有了，定时的本质就是
    「到点往队列塞一个 run」，和 reconciler 同一个位置（`worker.tick()` 里，
    在 `claimNext` **之前** —— 这样刚到点的任务同一轮就能被领走）。

    **每次新建会话，不注入上次结果。** 每次运行都是一件独立的新工作，
    只告诉它任务目标。附带好处：会话不会无限增长，**cron 因此不依赖 compact**。

    以后若想要「别重复昨天已经报过的内容」这类跨运行的记忆，那属于 L2
    事实层，不是会话连续性 —— 两者不要混。

    落地时改了两处设计，都是被测试逼出来的：

    - **`next_fire_at` 的推进基准是 `now`，不是最后一个计划点。**
      从计划点往后推的话，一个「逾期三小时」的每小时任务会在 `next` 仍然
      `<= now` 时被下一个 tick 再次领走，一路补到追平 —— 那恰恰是
      `catch_up=false` 要避免的「笔记本合盖一晚上，醒来跑 8 次」。
    - **补偿要反向取。** `plannedBetween` 的上限卡在前端，拿到的是**最早**的
      N 个；补跑日报你要昨天那份，不是三天前那份。所以加了 `prevFireAt` /
      `latestPlanned`，迭代次数恰好等于 N，与关机时长无关。

    三个语义的最终选择：
    - **停机补偿**：per-schedule 的 `catch_up`，默认**关**；`catch_up_max`
      默认 3。开了也只补最近 N 次。
    - **重入**：上次没跑完就**跳过**，不排队 —— 每小时一次的任务如果单次要跑
      两小时，排队会越积越多，而「跳过」在语义上是对的（同一件工作还在做）。
    - **幂等键**：`sched:<id>:<计划时刻截到分钟>`，靠 `runs.idempotency_key`
      的 unique 约束挡重复。**用唯一索引而不是先查后写** —— 两个 worker 同时
      到点是 TOCTOU，查重挡不住。

    **`schedule_fires` 表（一个计划点一行，append-only）**是这块最重要的一个
    补充，它不在原计划里。理由：`run_events.run_attempt_id` 是 not null，
    而**被跳过的触发根本没有 run**。而「今天早上 8 点那次到底跑没跑」恰恰是最
    需要事后能查的事 —— 没有这张表，症状就只是「产出不再出现」。

    `planned_at` 与 `fired_at` 分两列存：差值就是延迟/补偿的证据。

    连带修掉的一类**显示性谎言**：`outcome='fired'` 只说明**触发**成功，
    run 可能随后就失败了。对着一个 `config.agent_not_found` 的 failed run 打
    绿勾，和之前「系统会自动重试」那句假话是同一类错误。所以 `history`、
    `doctor`、诊断包三处都按 **run 的最终状态**判定，不按触发结果。

    入口：`nucleus schedule list|add|rm|enable|disable|history`。
    `doctor` 会报出指向不存在 agent 的计划（这是「产出静默消失」最常见的成因），
    诊断包把计划定义与最近 10 次触发结果一并带上。

19m. **预算写死 40k，与模型窗口无关；判据用条数而不是 token** ✅ 已修

    窗口本来就是按模型取的（`contextWindowFor` 取链上最小值），但预算被一个
    与窗口无关的硬上限卡住：

        historyBudgetFor(window) = min(40_000, window - 16_000)

    | 窗口 | 旧历史预算 | 旧触发 | 新历史预算 | 新触发 |
    |------|-----------|-------|-----------|-------|
    | 131k | 40.0k | 28.0k | **84.6k** | 59.2k |
    | 205k | 40.0k | 28.0k | **129.0k** | 90.3k |
    | 1M   | 40.0k | 28.0k | **705.3k** | 493.7k |

    **1M 窗口的模型会在用掉 3% 的时候开始压缩** —— 而每次压缩是一次模型调用
    加一次不可逆的信息损失，窗口里还空着 97%。

    `reserveForOutput: 16_000` 写死同样错：对 maxTokens=8192 的模型多留一倍，
    而在 20k 窗口的模型上它一个人吃掉 80% 的可用空间。正确来源是**模型自己
    声明的输出上限** —— 那才是「它可能吐多少」。

    改法（`src/context/budget.ts`）：

        输出余量 = 链上最大 maxTokens × 1.25   （下限 1k，最多占窗口一半）
        历史预算 = (窗口 − 输出余量) × 0.7
        摘要 / 约束块 = 按比例，但有上下限

    摘要有上限是刻意的：1M 窗口下让摘要涨到 80k 没有意义 ——
    摘要的价值在于短，长到那个程度不如直接放原文。

    输出上限取链上**最大**值而窗口取**最小**值 —— 两个方向都保守。降级到一个
    配了更大 maxTokens 的模型时，按小的那个留余量会让它一吐长就撞窗口。

    **判据也从条数改成 token**：
    - `keepRecent: 10`（条）→ `keepRecentRatio: 0.3`（占预算的比例）+
      `keepRecentMin: 2`（下限）。一条粘贴的日志可能顶几十条对话，
      「最近 10 条」在那种情况下能占满整个窗口。
    - `minRetire: 3`（条）→ `minRetireTokens: 2000`。退役 3 条小消息省不下什么，
      退役 1 条巨大的日志能省很多 —— 值不值得取决于 token。
    - 判定顺序也改了：**token 阈值是第一判据**，然后才算退役哪些。

    预算也进了 `context.assembled` 事件 —— 「为什么这一轮裁得这么狠」取决于
    当时算出来的预算，而不是某个常量。

19l. **两条触发条件里有一条从来不改变结果** ✅ 已修

    判定原本是三条：`fresh < minMessages(8)` → token 阈值 → `retireCount <= 0`。
    而第一条被第三条**严格包含**（`fresh < 8` 一定也 `fresh <= 10`），
    所以它从来不改变结果，只换一句措辞 —— 而那句措辞还不如第三条准确：
    5 条时真实原因是「不够 10 条，没有可退役的」，不是「不值得调一次模型」。

    有一条测试就叫「消息太少就不压缩 —— 不值得一次模型调用」并断言
    `reason` 含「不值得」。**测试名与断言一起指向错误的原因，而它照样是绿的。**

    `minMessages` 的**本意**是对的（别为一点点东西调一次模型），但它盯错了
    对象：该盯**要退役多少条**，不是总共有多少条。真正没被挡住的是另一头 ——

        fresh = 11, keepRecent = 10  →  退役 1 条

    这种情况原来**会真的压缩**：调一次模型给一条消息做摘要，纯浪费。

    改成 `minRetire`（默认 3，作用在 retireCount 上）。手动压缩降到 1 ——
    `conv compact` 的语义是「我现在就要压」，「值不值得」该由人判断。

19k. **降级顺序把摘要整个丢掉，包括用户约束** ✅ 已修

    而且**摘要是结构化的，本来就能按段降级** —— 这正是结构化的好处，
    却完全没被用上。丢掉 `context` 那段散文能省下大部分体积，
    而 constraints 全部保住。

    已加一档 `summary_to_constraints`，排在 `drop_summary` 之前：
    只留「要求 + 未决」。装配器仍然只按预算取舍、不懂摘要的内部结构 ——

    终端上两档分开显示：「摘要降到只剩要求」与「丢弃摘要（连用户约束一起）」
    —— 严重性差别很大，混成一句话会让人以为都一样。

19i. **「3 条约束都在 ✓」是过度解读，seed 已重写。**

    第一版只埋三句固定的话，固定在第 2/5/9 轮。而那三句都是**最好认的形状**：
    以明确标记开头（「有一条你要一直记着」）、都用「不要 / 必须」、都是自足单句。

    **对着 n=3 的固定集调 prompt 就是过拟合。** 而且它测不到三种真会出问题的：

    - **诱饵** —— 用了「必须 / 不能」但是技术陈述，不是用户要求。混进
      `constraints` 会让约束段逐代变脏，而原来那版「3/3 ✓」照样报绿
    - **撤销** —— 约束后来被取消。摘要留着已撤销的约束**比丢掉一条更糟**：
      模型会照它拒绝你现在想要的东西，而你不知道它为什么在拒绝。
      这一类我第一版完全没想到
    - **委婉表达** —— 没有「不要 / 必须」，关键词根本筛不出来

## H. 多 agent 来回交流（orchestrator ⇄ A ⇄ B）

22. **现在是单向流水线，想要的是多轮协商。**

    现在：`orchestrator → 专家A → 结果 → orchestrator → 专家B → 结果`。
    一次传输、拿结果、结束。想要的是三方来回：A 做到一半问 B 一句、B 回，
    A 再问编排者确认一个前提，然后才交付。

    直觉上产出会更好，理由也站得住：一次性传输要求上游**在开始前就把信封
    写全**，而很多前提是做到中途才发现缺的。现在缺前提的专家只有两条路 ——
    自己猜，或者在 open_questions 里留一句然后交差。两条都不好。

    ── **但这条要动的是最核心的不变量，不能顺手加** ──────────

    a) **wake/join 现在是一次性的。** 父 arm 一个 wake 等 N 个子，子写终态
       → 递减 → 归零唤醒父。而「问一句等一句」要求子 run **不进终态就能等**
       —— 那是一个新状态（`waiting_reply`），形状与 `ask_user`（D 块）完全
       一样：一个 run 等一个外部答复。**所以 D 是这块的前置**，不是并行项。

    b) **A ⇄ B 是兄弟通信，而现在只有父→子。** `delegate` 的语义是「派生一个
       子 run」，不是「给某人发消息」。兄弟通信需要：寻址（A 怎么指名 B？
       用 agent id 还是 run id？），以及一个新权限 —— 现在的 `delegate`
       授权的是「可以派活」，不等于「可以找任何人搭话」。

    c) **终止性是最大的风险。** 两个 agent 可以无限来回，而且每一轮都在花钱。
       `maxRunsPerRoot: 32` 管不住这个 —— 来回不新建 run，只是多几个 attempt。
       需要一个**按消息轮次**的预算，且超了要有明确的终止语义
       （谁做最终决定？编排者，还是各自交付现状？）。

    d) **context 会炸，而且炸在一个现在还没有 compact 的地方。**
       A 要不要看到完整的 A⇄B 线程？要看，context 就随轮次线性增长。
       而**子 run 现在没有 conversation、没有历史**（这是刻意的不变量：
       「子 run 没有对外身份」），也就是说压缩、预算、装配这一整套目前
       只服务 root run。给子 run 加线程等于给它们加历史。

    e) **「子 run 没有对外身份」这条不变量要不要破？** 不要。来回交流需要的是
       一个 run 之间的**线程**对象，与用户可见的 `conversations` 是两回事。
       混用会让专家的过程直接漏给用户 —— 那正是这个项目一开始要修的问题。
       所以需要新对象（暂称 `threads`），而不是复用 conversations。

    f) **「效果更好」目前是推测，得能量出来。** 同一个任务、同一批试题，
       单向 vs 多轮，比通过率与步数 —— `agent try --compare` 已经是这个形状，
       扩一下就能用。**先能量再优化**，否则会为了一个没验证的直觉付出
       3-5 倍的调用成本。

    建议顺序：**D（ask_user / waiting_reply）→ 兄弟寻址与权限 → 轮次预算与
    终止 → threads 对象与它的 context 装配 → 拿 try --compare 量效果。**
    在 D 之前动这块，等于同时开两个新状态机。
