按块组织，块内按依赖排序。每条都注明**为什么** —— 没有理由的待办过两周就没人知道该不该做。

标记：`[决定]` 待你拍板 · `[需要你]` 我做不了 · 其余我可以直接做。

## A. 自己定义专家的完整 workflow

目标：你只描述想要什么，系统帮你把它变成一个能跑、能验、能迭代的专家。
现在的状态是「只能改一个整体替换的 JSON 数组，改完只能跑整条编排来试」。

顺序有依赖，不能打乱：

1. **任务信封结构化** —— `delegate({agent, goal, context, acceptance, why})`
   替掉现在的自由字符串 `task`，并定义专家实际收到的**渲染**。
   为什么先做：专家**看不到会话历史**（刻意设计，它没有对外身份），
   所以信封必须自足；而现在「包含必要上下文与验收标准」只是工具描述里的一句
   劝导，没有任何东西保证它真的包含。改成 schema 字段就从劝导变成契约，
   缺失率也能统计。
   附带：`why`（为什么选这个专家）让选择依据显式化，派错时它就是诊断材料。
   **必须先于 4/5**：`agent new` 的骨架里要写明「你的专家会收到什么」。

2. **可声明的结果段** —— 替掉写死在 TS 里的 `'research' | 'code'`。
   现在 `CAPABILITY_SCHEMAS` 是硬编码的两个段，所以你没法让一个金融分析专家
   必须交出 `metrics[{name, value, asOf, source}]`。
   而 `resultJsonSchema` / `validateResult` / `agent show` 三处已经是数据驱动的，
   只是数据源写死了。
   **必须先于 5**：否则 LLM 生成定义时，输出形状只能在 research/code 里选。

3. **`agents/*.md` 加载器**
   - 一个专家一个文件，天然增量（加文件不会删掉别人）
   - prompt 是正文而非 `\n` 转义串 —— 而 prompt 是你改得最勤的东西，
     diff 可读性直接决定迭代速度
   - **同时保留 `nucleus.config.json` 里的 `agents`**，doctor 报出每个 agent
     来自哪。留 `agentsDir` 口子给机器专属的专家
   - `agents/` **进 git**（定义要版本化、要能 diff、换机器要跟着走）；
     `nucleus.config.json` 保持 gitignore（机器相关：有哪些模型、数据库地址）
   - **试题集单独文件** `agents/<id>.cases.md`：定义保持短小可读，
     加一道题不显示成「这个 agent 变了」，而且「cases 不进 context」
     这件事从文件布局上就看得出来
   - 强断言：装配出的 prefix 里**不得出现试题文本**（与现有「前缀里不能有
     时间戳」同一类的守护）

4. **`nucleus agent new <id>`** —— 空骨架，离线可用。
   骨架里直接写 `whenToUse` 的正例反例：

   ```
   ✗ 调研                          ← 名词，模型难判断
   ✗ 负责研究相关任务              ← 同义反复
   ✓ 需要查外部资料、且结论必须带可验证来源时
   ```

5. **`nucleus agent new --describe "..."`** —— LLM 生成完整定义。
   之所以比一般的「让 LLM 写 prompt」靠谱：系统手里有它需要的全部素材
   —— 权限词表（含每项的 risk）、已注册工具（描述 + 所需权限 + 副作用等级）、
   现有专家名册（用来**避开语义重叠**）、结果契约选项。

   三条硬性设计：
   - **权限单独确认**。LLM 顺手给个 `execute` 完全可能，所以生成的权限要
     连风险一起列出来让你确认，不能默默生效
   - **必须真实模型**。没配模型时直接报错，而不是拿 mock 生成一份像样的垃圾
   - **说清它写不出什么**。LLM 不知道你的数据源和验收标准，生成的 `whenToUse`
     会「读起来合理但偏泛」。修正靠第 6 条那个循环，不是靠再生成一遍

6. **`nucleus agent try <id> "任务"`** —— 只跑这一个专家，不经编排者、不委派。
   现在试一个专家只能跑整条编排，几分钟一轮，而且结果不好时分不清是
   编排者派错了、任务描述太烂、还是专家本身不行。

   **从第一版就要带 `--n` 和 `--compare`**，不能先做单跑版 ——
   单跑版会让人以为「跑过了就是好了」，那比没有更糟。

   打印：调了哪些工具、**有没有想调没权限的工具**、契约过没过/退回几次/缺哪个
   字段、产出多大、token 与耗时。

7. **`nucleus agent diff` + 回归判据**
   目标不是「证明更好」（单跑一次证明不了任何事，模型有随机性），
   而是**让退步无法悄悄溜过去**：

   - 固定试题集 —— **在不同任务上比两个定义，「更好」没有意义**
   - `--n 5` 重复跑取通过率，一次是噪音
   - `--compare HEAD~1` 与上一版并排（`agents/*.md` 在 git 里，上一版拿得到）
   - **权限面绝不能悄悄变宽** ← 纯静态、零成本、零噪音，能挡一大类真实退步
   - 越权尝试次数：它想调没权限的工具，说明 prompt 与权限不匹配

   能自动判的到此为止。**答案内容好不好系统判不了** ——
   要么你自己读（`nucleus artifact cat`），要么用裁判 agent 按信封里的
   `acceptance` 打分（这是把信封结构化的额外回报）。

   诚实的上限：在 3 道题上更好的定义，第 4 道题上可能更差。消不掉，
   只能让试题集随踩坑不断长大，逐渐变成回归集。

8. **移除内置的 researcher / operator**。你要自己定义专家。
   留 `orchestrator`（它是基础设施：入口 + 委派 + 整合，不是专家）。
   31 处引用要改：测试与 `verify` 改用单独导出的示例集。

## B. 可靠性

9. **run 级重试** —— 这是剩下最大的可靠性洞，也是第 6 处「声明了没接线」。

   `recovery: 'automatic'` 界面说「系统会自动重试」，但 attempt 失败后 run
   直接落 terminal `failed`，队列是空的。真正的重试只发生在一次 `chat()`
   内部（就地重试 + 模型链降级）。`runStatusOverride`（注释写着「failed 但
   还要重试 → waiting_retry」）**没有任何调用方传它**。

   后果就是最初抱怨的那类：四个模型同时被限流 → run 直接死 → 得重新发一遍，
   而界面还说它会自己恢复。

   要做：退避 + 上限 + 调度。`run_queue.available_at` 已经有了，不用新表。

10. **compact** —— 现在超预算是**丢**最旧的消息，不是压缩。

    装配器的降级顺序里有 `shrink_summary` / `drop_summary` 两档，`summary`
    也是它的入参，但**没有任何代码产生摘要**，所以那两档永远不会触发。
    长会话里早期内容被静默丢掉（现在至少终端会显示「裁掉 N 条历史」）。

    也是 cron 选「固定长期会话」的前提。

11. **装配器另外两个空入口** —— `facts`（L2 事实层）与 `constraints`（T1 注入）
    同样没人喂。`constraints` 归 C 块；`facts` 是 L2 记忆，可以更晚。

## C. 规则

12. **规则作者单元** —— 一条规则同时携带三层，运行时按字段决定它落到哪层：

    ```jsonc
    { "id": "cite-sources",
      "constraint": "每条 finding 至少一个可验证来源。",   // T1 注入末尾约束块
      "check": { "requiredFields": ["findings[].sources"] }, // T2 校验
      "denyTools": [],                                       // T3 边界
      "appliesTo": ["researcher"] }
    ```

    两条原则：
    - **T1 必须配 T2**。只写 T1 等于把「prompt 写满禁止但模型照犯」原样搬回来
    - **能用 T3 表达的绝不写成 T1**。T3 零成本且不可违反；T1 只在无法用能力
      边界表达时才用（「结论要标来源」没有任何工具开关能阻止）

13. **T1 注入**到末尾约束块。`buildTail()` 与 `maxConstraintTokens` 预算都已存在，
    且刻意放在最后以免破坏前缀缓存 —— 只是没人调。

14. **per-rule 遵守率**。现在 `nucleus rules` 只能按**字段**统计。
    规则有了 id 之后就能按规则给出数字 —— 这才让「加规则」变成可收敛的动作。

15. **委派准确率**。数据是现成的（`delegate` 意图记了目标 agent，子 run 终态
    已知），所以「派给 X 的任务里多少失败/被退回」可以算。
    这比反复猜 prompt 措辞强，因为它可收敛。

## D. 编排者作为对话层

16. **`ask_user`** —— 编排者现在**不能反问用户**。全项目没有这个工具，
    唯一的人工介入是 `needs_human_confirmation`（副作用未知时），
    那是个死胡同状态而不是对话。需求含糊时它只能猜。

    复用 wake 机制，几乎不用新东西：问题以 assistant 消息写进会话 → run 落
    `waiting_user`、attempt 结束（不占进程不占 context）→ 用户下一条消息
    就是唤醒信号。与 `delegate` 完全同构。

    `[决定]` `waiting_user` 期间会话锁不锁？倾向锁（`active_run_id` 本就是
    「同会话 run 串行」的乐观锁）。

17. **名册进 segment ②**。现在只在 `delegate` 的工具描述里（选择发生的地方，
    这是对的）。system prompt 里再放一份**决策方法**（怎么拆解、什么该自己答），
    但**不放工具/权限清单** —— 编排者不调那些工具，给它看会诱导越级指挥，
    还把它和会变的工具名耦合起来。

## E. cron

18. **`schedules` 表 + worker tick 里的 `#fireDueSchedules()`**。
    不需要新进程：`run_queue.available_at` 已经有了，定时的本质就是
    「到点往队列塞一个 run」，和 reconciler 同一个位置。

    `[决定]` 四个语义：
    - **跑在哪个会话里**：每次新建（干净但无连续性）/ 固定长期会话（有连续性
      但会越来越长，直接撞上 compaction 缺失）/ 每次新建 + 注入上次摘要。
      倾向第三个
    - **停机补偿**：关机三天后补跑三次还是只跑最近一次？「每日简报」补跑是
      噪音，「对账」类必须补 —— 所以是 per-schedule 开关，不是全局默认
    - **重入**：上次没跑完又到点 —— 跳过 / 排队 / 并行。默认建议跳过并记事件
    - **幂等键**：用**计划**触发时间而不是实际触发时间，这样 reconciler 重放
      不会重复外部副作用

## F. 诚实性与技术债

19. **README / DESIGN 的现状段改准**。它现在有过时之处：说「前沿模型遵守率
    未知」（真实 GLM 已验，0 次契约退回）、四个订阅模型的风险项（模型已移出
    默认配置）、以及把「context 装配」列在已完成里（那句在接线之前不成立）。
    **一份会骗人的现状清单比没有更糟。**

20. **6 张建了从没写过的表** —— 每张代表一个只有 schema 的功能：
    `tasks` + `activity_logs`（任务看板 / 计划式编排）、`prompt_versions`
    （prompt 版本化与归因）、`tool_snapshots`（工具集快照）、`mcp_servers`
    （MCP 运行时状态持久化，现在只在内存里、重启就丢）、`usage_log`
    （逐次调用用量明细，现在只有 attempt 级聚合）。

    要么接上，要么删掉。留着是误导 —— 看表判断进度会系统性高估。

21. **自动检查「声明了没接线」**。这一路撞了 8 次：

    规律很清楚：**这个仓库里 schema 和类型跑得比实现快。** 至少该有一条
    「每张表都有 INSERT」「每个声明的字段都有写入方」的检查跑在 CI 里。
