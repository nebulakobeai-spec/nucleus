## B. 可靠性

9. **run 级重试** —— 这是剩下最大的可靠性洞，也是第 6 处「声明了没接线」。

   `recovery: 'automatic'` 界面说「系统会自动重试」，但 attempt 失败后 run
   直接落 terminal `failed`，队列是空的。真正的重试只发生在一次 `chat()`
   内部（就地重试 + 模型链降级）。`runStatusOverride`（注释写着「failed 但
   还要重试 → waiting_retry」）**没有任何调用方传它**。

   后果就是最初抱怨的那类：四个模型同时被限流 → run 直接死 → 得重新发一遍，
   而界面还说它会自己恢复。

   要做：退避 + 上限 + 调度。`run_queue.available_at` 已经有了，不用新表。

10. **compact** —— 现在超预算是**丢**最旧的消息，不是压缩。

    装配器的降级顺序里有 `shrink_summary` / `drop_summary` 两档，`summary`
    也是它的入参，但**没有任何代码产生摘要**，所以那两档永远不会触发。
    长会话里早期内容被静默丢掉（现在至少终端会显示「裁掉 N 条历史」）。

    也是 cron 选「固定长期会话」的前提。

11. **装配器另外两个空入口** —— `facts`（L2 事实层）与 `constraints`（T1 注入）
    同样没人喂。`constraints` 归 C 块；`facts` 是 L2 记忆，可以更晚。

## C. 规则

12. **规则作者单元** —— 一条规则同时携带三层，运行时按字段决定它落到哪层：

    ```jsonc
    { "id": "cite-sources",
      "constraint": "每条 finding 至少一个可验证来源。",   // T1 注入末尾约束块
      "check": { "requiredFields": ["findings[].sources"] }, // T2 校验
      "denyTools": [],                                       // T3 边界
      "appliesTo": ["researcher"] }
    ```

    两条原则：
    - **T1 必须配 T2**。只写 T1 等于把「prompt 写满禁止但模型照犯」原样搬回来
    - **能用 T3 表达的绝不写成 T1**。T3 零成本且不可违反；T1 只在无法用能力
      边界表达时才用（「结论要标来源」没有任何工具开关能阻止）

13. **T1 注入**到末尾约束块。`buildTail()` 与 `maxConstraintTokens` 预算都已存在，
    且刻意放在最后以免破坏前缀缓存 —— 只是没人调。

14. **per-rule 遵守率**。现在 `nucleus rules` 只能按**字段**统计。
    规则有了 id 之后就能按规则给出数字 —— 这才让「加规则」变成可收敛的动作。

15. **委派准确率**。数据是现成的（`delegate` 意图记了目标 agent，子 run 终态
    已知），所以「派给 X 的任务里多少失败/被退回」可以算。
    这比反复猜 prompt 措辞强，因为它可收敛。

## D. 编排者作为对话层

16. **`ask_user`** —— 编排者现在**不能反问用户**。全项目没有这个工具，
    唯一的人工介入是 `needs_human_confirmation`（副作用未知时），
    那是个死胡同状态而不是对话。需求含糊时它只能猜。

    复用 wake 机制，几乎不用新东西：问题以 assistant 消息写进会话 → run 落
    `waiting_user`、attempt 结束（不占进程不占 context）→ 用户下一条消息
    就是唤醒信号。与 `delegate` 完全同构。

    **已定：锁。** 你下一条消息就是对那个提问的回答；想开新任务用 `/new`。
    不锁的话系统得猜「这句是答案还是新任务」，而猜错的代价是把回答喂给
    错误的 run。

    实现上不用新东西：`conversations.acquire()` 已经用条件更新做好了
    「同会话只允许一个活跃 run」的 CAS。**但它目前只有自己的测试在调用**
    （第 9 处「声明了没接线」）—— 所以这一条其实是两件事：接上那把锁，
    再加 `waiting_user` 状态。

    今天还没出问题只是因为 CLI 与 REPL 都是串行的；一旦有并发入口
    （或者两个 CLI 同时跑同一个会话）就会两个 run 抢一个会话。

17. **名册进 segment ②**。现在只在 `delegate` 的工具描述里（选择发生的地方，
    这是对的）。system prompt 里再放一份**决策方法**（怎么拆解、什么该自己答），
    但**不放工具/权限清单** —— 编排者不调那些工具，给它看会诱导越级指挥，
    还把它和会变的工具名耦合起来。

## E. cron

18. **`schedules` 表 + worker tick 里的 `#fireDueSchedules()`**。
    不需要新进程：`run_queue.available_at` 已经有了，定时的本质就是
    「到点往队列塞一个 run」，和 reconciler 同一个位置。

    **已定：每次新建会话，不注入上次结果。** 每次运行都是一件独立的新工作，
    只告诉它任务目标是什么，与上一次的运行结果无关。

    一个附带好处值得记下：这样会话不会无限增长，**cron 因此不依赖 compact**
    —— 原来担心「固定长期会话会撞上 compaction 缺失」的问题不存在了。
    所以 E 可以提前到 B10 之前做。

    以后若想要「别重复昨天已经报过的内容」这类跨运行的记忆，那属于 L2
    事实层，不是会话连续性 —— 两者不要混。

    剩下三个语义：
    - **停机补偿**：关机三天后补跑三次还是只跑最近一次？「每日简报」补跑是
      噪音，「对账」类必须补 —— 所以是 per-schedule 开关，不是全局默认
    - **重入**：上次没跑完又到点 —— 跳过 / 排队 / 并行。默认建议跳过并记事件
    - **幂等键**：用**计划**触发时间而不是实际触发时间，这样 reconciler 重放
      不会重复外部副作用
